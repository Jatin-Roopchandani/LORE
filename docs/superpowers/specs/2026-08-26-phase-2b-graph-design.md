# LORE Phase 2B — Entity Resolution & Graph Build Design

**Status:** approved in chat 2026-08-26. Implements the second half of SPEC.md §9 Phase 2.

**One sentence:** `lore process <book>` takes a book from file to a browsable knowledge graph — resolving "Lady Danholm" and "Sera Danholm" into one node, normalising predicates, and loading entities, relationships and vectors transactionally — after which a multi-hop Cypher query returns a correct, evidence-carrying answer.

---

## 1. What Phase 2A left us

2A produces, per work unit, on disk:

- `triplets.parquet` — `chunk_id, book_id, subject, predicate, object, evidence, confidence, entity_names[], entity_kinds[], extractor_model, run_id`
- `embeddings.parquet` — `chunk_id, vector(768), embed_model`
- `dead_letter.jsonl`, `manifest.json`

These are validated but **inert**: strings, not nodes. 2B turns them into a graph.

The stores already exist with their schemas (Phase 0): Kuzu holds `Book`, `Chapter`, `Chunk`, `Entity` nodes and `HAS_CHAPTER`, `HAS_CHUNK`, `MENTIONS`, `ALIAS_OF`, `REL` relationships; LanceDB holds a `chunks` table (vector + `entity_ids[]` bridge) and an `entities` table (name/kind centroids). Nothing has ever been written to either.

## 2. Locked decisions

| Decision | Choice | Rationale |
|---|---|---|
| Entity scope | **Cross-book, higher bar to merge** | Cross-book queries are the project's premise; per-book nodes make them impossible. Same-book merges may pass on embedding similarity alone; cross-book merges require a higher floor **and** mandatory LLM adjudication, so "the Captain" in two unrelated novels stays two people. |
| Predicates | **Store raw + normalized** | The 7B model emits `COMMANDS`/`DISTRUSTS` where the curated set says `ALLEGIANCE_TO`/`OPPOSES`. Traversal uses the normalized field; the raw one preserves nuance that `OPPOSES` would flatten. |
| Confidence | **Load everything, filter at query time** | Every edge carries its confidence. Thresholds can be tuned after seeing real distributions; discarded edges would require re-extracting the library to recover. |
| Scope | **One plan for all of 2B** | Resolution's output is the loader's input; designing the loader against artifacts that do not exist yet would be guesswork. |
| Adjudication backend | **Local Ollama** | Gray-band decisions are a handful of cheap yes/no calls. Zero Kaggle quota, and it keeps resolution runnable offline. |

## 3. Development and acceptance strategy

Build against artifacts generated by the **local Ollama tier** — fast, free, no quota, and enough to exercise every code path. Use a **full Kaggle-extracted Pride and Prejudice** for acceptance.

This also discharges 2A's parked regeneration item: the front-matter filter changed chunk ids and the artifact contract gained `book_id`, `entity_kinds` and timestamps, so the five P&P units extracted during 2A are stale and must be regenerated regardless.

## 5. Entity resolution

The problem: chunk 40 says "Elizabeth", chunk 380 says "Miss Bennet", chunk 500 says "Lizzy". Three strings, one person.

**Pass 1 — exact / alias.** Normalise the surface name (casefold, strip punctuation and possessives, drop honorifics such as Mr/Mrs/Miss/Lady/Lord/Captain) and look it up against canonical entities and their alias lists. A hit resolves immediately. `lore/resolve/normalize.py` holds these pure functions and carries the heaviest test burden in the phase — most false merges are won or lost here.

**Pass 2 — embedding similarity.** Embed `name + local context` and compare against each candidate canonical entity's centroid, restricted to the same `kind`. Above the merge floor, merge; below the reject floor, mint a new entity; in between, escalate.

**Pass 3 — LLM adjudication.** Only the gray band reaches an LLM: a cheap yes/no on local Ollama, given both entities' names, kinds and evidence quotes. Same-book pairs may resolve on pass 2 alone; **cross-book pairs always reach pass 3** and must clear a higher pass-2 floor to get there.

Every merge writes an `ALIAS_OF` edge, so merges are auditable and reversible rather than silent overwrites.

**Entity ids** are minted deterministically from the first normalised name that created the entity plus its kind, so a rebuild from the same artifacts reproduces the same ids.

## 6. Predicate normalization

Each raw predicate is mapped to the nearest of the ten curated types (`ALLEGIANCE_TO, MEMBER_OF, LOCATED_IN, POSSESSES, INTERACTS_WITH, OPPOSES, LOVES, KILLS, BECOMES, EXPERIENCES`) by embedding similarity. Below the threshold it becomes `UNCATEGORIZED`. The raw string is always preserved.

**Schema change:** Kuzu's `REL` table gains `predicate_raw STRING` alongside the existing `predicate`, which now holds the normalized value. This is the only schema change 2B requires.

## 7. The load

Per book, in one transaction, idempotent:

1. `Book`, `Chapter`, `Chunk` nodes with `HAS_CHAPTER` / `HAS_CHUNK` structure, from the SQLite registry.
2. `Entity` nodes for every canonical entity, plus `ALIAS_OF` edges recording merges.
3. `MENTIONS` edges from chunks to the entities they name.
4. `REL` edges carrying `predicate` (normalized), `predicate_raw`, `evidence`, `confidence`, `chunk_id`, `book_id`, `chapter_seq`, `run_id`.
5. LanceDB upserts: `chunks` rows (vector, text, `entity_ids[]` bridge) and `entities` rows (centroid, name, kind).

**The loader gates on job state, never file presence.** A failed unit legitimately leaves logs and partially pulled artifacts in its directory; only units whose `jobs` row reads `completed` may be loaded.

Re-loading a book must not duplicate nodes or edges.

## 8. CLI

- `lore process <book_id>` — the full chain: extract (delegating to 2A's orchestrator, honouring `--resume`), resolve, load. Reports entity and edge counts.
- `lore graph` — node and edge counts by type, plus the most-connected entities. The cheapest way to see whether a book actually produced a graph worth querying.

## 9. Testing

- **Unit:** normalization, predicate mapping, resolution passes with a fake embedder and fake adjudicator, loader writes into a `tmp_path` Kuzu/LanceDB — all offline, no network, no GPU.
- **Resolution quality:** a hand-built fixture with known aliases ("Elizabeth Bennet" / "Miss Bennet" / "Lizzy") asserting they collapse to one entity while a genuinely different character does not.
- **Cross-book guard:** two books each containing "the Captain" must NOT merge without adjudication approving it.
- **Idempotency:** loading the same book twice leaves identical node and edge counts.
- **Acceptance:** load a Kaggle-extracted Pride and Prejudice and run a real multi-hop Cypher query.

## 10. Exit criteria

1. `uv run pytest -m 'not live'` green, output pristine.
2. `lore process <book_id>` takes an ingested book to a loaded graph without manual intervention.
3. Aliases collapse: a character named three ways in the text is one `Entity` node with `ALIAS_OF` provenance for each merge.
4. Re-running the load is idempotent — identical counts, no duplicate edges.
5. `lore graph` reports node and edge counts for a real novel.
6. **The killer demo:** a multi-hop Cypher query over the loaded graph returns a correct answer with evidence quotes and chapter numbers attached — a question plain vector search over the same chunks demonstrably cannot answer.
